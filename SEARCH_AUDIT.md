# Проверка мониторинга Kufar

## Подтверждённая причина текущего отказа

На сервере выполнена отдельная проверка версии 2.9.4. Оба адреса поиска вернули HTTP 403 и текст Kufar об ограничении доступа из локации сервера. Проверка не читает конфигурацию, не читает и не меняет кеш, не вызывает Telegram. Следовательно, этот отказ происходит до фильтрации, сравнения ID и отправки объявлений.

По сообщению владельца, прежняя копия работала на Railway. До версии 2.9.4 использовался прежний адрес `searchapi.kufar.by/v1/search/rendered-paginated`; сравнение истории `f18d761..6712c82` не показывает изменения способа отправки поискового HTTP-запроса в `networking.cpp`. Изменения парсера в `kufar.cpp` обрабатывают успешный ответ и не могут создать ответ 403 от сервера Kufar. `railway.json` не менялся в этом диапазоне; Docker остался на Debian bookworm, изменилось лишь число параллельных потоков сборки.

Доступ к Railway сейчас не проверен: владелец сообщил, что копия отключена. Нет доступа по SSH для изменения маршрута сервера. Нельзя считать проблему поиска решённой, пока проверка API из фактически работающего контейнера не вернёт корректный массив `ads`.

## История двух ответов в Telegram

В переписке зафиксированы одновременно пустой список запросов и старый список из другой копии. После остановки серверного контейнера сообщения продолжались. Владелец определил источник как Railway и отключил его. Это две установки с независимыми конфигурациями и кешами. Блокировка файла состояния защищает общий кеш, но не может остановить процесс на другом хосте. Отключение второй копии устраняет эту подтверждённую причину двойных ответов; дедупликация событий дополнительно защищает каждый экземпляр.

## Проверенные части проекта

- Конфигурация: переменные окружения, пользователи, поиски из JSON и сохранённые изменения меню. Пустой пользовательский override сохраняет удаление старых запросов после перезапуска.
- HTTP: код статуса проверяется до разбора JSON; резервный API получает те же фильтры; токены и произвольные тела HTTP-ошибок не выводятся в диагностике.
- Парсер: отсутствующие необязательные цены, фото, продавец и телефон; отдельные повреждённые объявления; полностью некорректная выдача не инициализирует поиск.
- Мониторинг: изменение запросов и `/check` прерывают ожидание цикла; первая выдача молчит; новая выдача сравнивается с историей; неудачная отправка остаётся для повторной попытки; последняя успешная проверка сохраняется.
- Telegram: права владельца, приватные чаты, сохранение update/message ID, старые клавиатуры удаления и группировка словоформ.
- Хранение: атомарная замена кеша, предел 500 МиБ, резерв свободного места, срок хранения, лимиты записей, сохранение остальных пользователей при очистке запросов владельца.
- Развёртывание: обычное обновление, установка из архива, sudo, сборка до замены контейнера, постоянные mounts данных, контроль перезапусков.

## Найденные и исправленные ошибки

1. Добавленный во время ожидания поиск мог ждать полного старого интервала. Исправлено в 2.9.3.
2. Сортировка старого запроса по цене могла оставлять новое объявление за пределами страницы. Мониторинг использует сортировку по новизне с 2.9.4.
3. Первое наполнение одного поиска молча записывало объявление в общую историю и могло подавить его отправку в другом, уже активном поиске. В 2.9.5 отдельно сохраняется, какие поиски запомнили объявление без доставки. Успешная отправка подтверждает доставку для всех поисков пользователя; неуспешная остаётся для повтора. Отдельный сценарий проверяет пересекающиеся поиски и перезапуск.
4. Поиски из старой конфигурации с одинаковым названием использовали один маркер инициализации независимо от категории. В 2.9.5 ключ учитывает конфигурацию запроса; прежние маркеры мигрируют без очистки истории и повторного молчаливого наполнения.
5. Скрипт обновления сообщал об успехе после проверки только состояния процесса. В 2.9.5 он также проверяет API из контейнера и явно сообщает недоступность поиска, сохраняя работающий контейнер и данные.
6. Подготовлена адресная настройка `KUFAR_PROXY`, позволяющая использовать предоставленное владельцем доступное подключение для API Kufar. Она не меняет подключение Telegram, не выводит адрес или пароль в диагностику и не подбирает внешний сервис автоматически. Настройка пока не применена на сервере: адрес подключения не предоставлен. Работа маршрута проверяется реальным libcurl через локальный тестовый CONNECT-прокси, включая влияние `NO_PROXY`, изоляцию Telegram и отсутствие пароля в ошибках. Механизм основан на [CURLOPT_PROXY](https://curl.se/libcurl/c/CURLOPT_PROXY.html) и [CURLOPT_NOPROXY](https://curl.se/libcurl/c/CURLOPT_NOPROXY.html).

## Границы проверки

Автоматические проверки транспорта поиска и Telegram используют контролируемые ответы и не доказывают доступ с IP сервера. Сборка и тесты выполняются на Linux в GitHub Actions. Живой бот на Windows не запускается.

Точная версия прежнего работающего контейнера Railway не предоставлена. Сравнение относится к доступной истории репозитория, а не к извлечённому бинарному файлу с Railway. Для старой истории кеша без отметок о доставке невозможно восстановить, какие ID были отправлены, а какие только запомнены; её подавление дублей сохраняется при миграции.

Мониторинг проверяет одну страницу на сохранённый запрос, обычно 30 объявлений, максимум 200. Если между проверками появляется больше объявлений, часть может не попасть на эту страницу. Это ограничение объёма выдачи; оно не объясняет полученные HTTP 403.

При отказе локации требуется доступное исходящее подключение для Kufar либо запуск единственного экземпляра на площадке, где поиск доступен. Автоматически включать прежнюю копию Railway при работающей серверной копии нельзя: это возвращает известную проблему двух ботов в одном чате. Конкретный сетевой маршрут и доступ к внешней площадке пока не предоставлены.
