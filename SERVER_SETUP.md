# Запуск бота на Linux-сервере

Понадобятся Docker Engine и Docker Compose, токен бота от @BotFather и ваш числовой Telegram ID. Для сборки желательно 2 ГиБ RAM и несколько ГиБ свободного диска. Входящие порты открывать не нужно. Серверу нужен исходящий HTTPS к Telegram и Kufar.

1. Установите Docker по официальной инструкции для [Ubuntu](https://docs.docker.com/engine/install/ubuntu/) или [Debian](https://docs.docker.com/engine/install/debian/), включая Compose plugin. На Arch можно использовать имеющийся `bash deploy-arch.sh --prepare`. Включите автозапуск Docker: `sudo systemctl enable --now docker`.
2. Скопируйте проект на сервер и перейдите в его папку. Выполните:

   ```bash
   bash deploy.sh --prepare
   nano .env
   ```

   Заполните `TELEGRAM_BOT_TOKEN`. В `TELEGRAM_CHAT_ID` и `TELEGRAM_ADMIN_ID` укажите **свой числовой ID**. Не оставляйте чужие значения из примера. Файл `.env` не публикуйте.

3. Напишите боту `/start`. Если переносите работающего бота, получите через `/backup` оба файла, остановите старую копию и положите конфигурацию в `kufar-configuration.json`, а историю — в `data/cached-data.json` **до запуска**. Старый `KUFAR_RECIPIENTS_JSON` в `.env` переопределяет восстановленную конфигурацию — уберите его, если восстанавливаете файл. Существующая история скриптом не удаляется.
4. Запустите:

   ```bash
   bash deploy.sh
   ```

   Сборка запускает автоматические тесты. После запуска скрипт проверяет, что контейнер работает и не перезапускается; соединение с Telegram проверьте командами `/menu` и `/status`. Одновременно должна работать только одна копия бота с этим токеном. Без перенесённой истории первая проверка каждого поиска запоминает текущие объявления без рассылки.

## Пользователи через Telegram

Владелец открывает `/users` или кнопку «👥 Пользователи». Новый пользователь пишет боту `/start` или `/id` и передаёт владельцу полученный ID.

- `/adduser 123456789` — подключить пользователя; можно также нажать «Добавить пользователя» и ввести ID следующим сообщением.
- `/removeuser 123456789` — запросить удаление; подтвердите кнопкой «Да, отключить». Запросы и история этого человека удалятся.
- `/menu` или «Отмена» — отменить незавершённое действие.
- `/backup` — скачать конфигурацию и историю для переноса.

Эти действия доступны только владельцу в личном чате. Владелец не может удалить себя. Добавления и отключения переживают перезапуск. Подключённый пользователь сам добавляет свои поиски через `/menu`. После повторного подключения удалённого пользователя его поиски настраиваются заново. Лимиты меню: 100 активных пользователей и 200 поисков по категориям на человека.

В списке запросов русские словоформы показываются одной группой: например, «Книга», «Книги», «Книжка», «Книжечка» и «Книжека». Под названием перечислены сохранённые варианты. Бот продолжает проверять каждый исходный запрос с его фильтрами и прежним кешем. Числа, модели, порядок слов и отрицание сохраняются, поэтому «гиря 24 кг» и «гиря 32 кг» — разные группы. Группировка учитывает обычные окончания русских существительных и прилагательных и распространённые варианты слова «книга»; произвольные синонимы и опечатки автоматически не угадываются. Удаление группы с подтверждением удаляет все её словоформы во всех категориях только у выбранного пользователя.

## Как ограничен расход диска

| Что хранится | Ограничение |
| --- | --- |
| История объявлений | 20 000 на человека, 100 000 суммарно |
| Срок истории | 180 дней с последнего появления в выдаче |
| `data/cached-data.json` | Не больше 500 МиБ при чтении и сохранении |
| Временный файл при сохранении | Один `.tmp`, не больше 500 МиБ |
| Логи контейнера | Ротация: 3 файла примерно по 10 МБ |
| Временные файлы `/tmp` | 16 МиБ в памяти |

Изменить количество и срок истории можно через `KUFAR_CACHE_*` в `.env` (см. `.env.example`). Старые объявления очищаются автоматически вместе с ценами и датами. После очистки очень старое объявление может прийти повторно, если вновь появится в поиске. Фото на сервер не скачиваются. Удалённые пользователи, добавленные через меню, не оставляют растущий список записей; для пользователей из начальной конфигурации сохраняется запрет доступа.

Перед записью бот проверяет, что после создания временного файла останется хотя бы 64 МиБ свободного места. Если места не хватает, достигнут предел 500 МиБ или запись не удалась, предыдущий файл сохраняется, процесс завершается с ошибкой; Docker пытается перезапустить его. Причина видна в логах. Освободите место или восстановите подходящую резервную копию при остановленном боте. Не удаляйте кеш вслепую: в нём также настройки пользователей и поисков. Проверка свободного места не резервирует диск и не защищает от одновременной записи других программ.

Предел кеша 500 МиБ — максимальный размер файла, а не резервирование памяти или обещание хранить столько данных при любых настройках. Лимиты 20 000 объявлений на человека и 100 000 суммарно сохраняются: при них обычный кеш гораздо меньше предела. Из-за загрузки JSON и цен в память очень большой кеш может потребовать больше установленного ограничения RAM 512 МиБ. На диске одновременно могут находиться основной файл и временная копия (до 1000 МиБ суммарно), плюс около 30 МБ логов. Это **не квота всего Docker**: образы, кеш сборки и сохранённые вами резервные копии учитываются отдельно. Бот автоматически не создаёт папки с ежедневными копиями. `/backup` отправляет документы только до 45 МиБ; больший кеш копируйте с сервера при остановленном боте.

```bash
df -h .
sudo du -sh data
sudo docker system df
sudo docker compose logs --tail=100
```

Владелец видит размер состояния и свободное место в `/status`. Для проверки занимаемого Docker места используйте `docker system df`. После обновлений при необходимости вручную удаляйте ненужный кеш сборки командой `sudo docker builder prune --filter until=168h` (затрагивает кеш сборок на всём Docker-хосте; запросит подтверждение). Не используйте очистку volumes для обслуживания этого бота.

## Обновление и остановка

В существующей папке репозитория выполните одну команду:

```bash
git pull --ff-only && bash update.sh
```

Если папка установлена из ZIP и Git сообщает `not a git repository`, подключите её к вашему репозиторию. В папке, где находятся `.env`, `compose.yaml` и `kufar-configuration.json`, выполните один раз:

```bash
curl -fL https://raw.githubusercontent.com/IDDQDD/Kufar-Telegram-Notifier/main/setup-git.sh -o /tmp/kufar-setup-git.sh && bash /tmp/kufar-setup-git.sh "$PWD"
```

Нужны Git и tar. Скрипт сначала скачивает ветку `main`, сохраняет текущий код и настройки в `backups/before-git-*.tar.gz`, подключает настоящую `.git` и обновляет код. `.env`, `kufar-configuration.json` и история остаются на месте. Конфигурация помечается в локальном индексе `skip-worktree`, чтобы серверные настройки не попадали в обычный статус изменений. Резервная копия содержит `.env`: доступ к файлу ограничен владельцем, не публикуйте её. Для дальнейшей разработки доступны обычные команды Git; следующие обновления выполняются через `git pull --ff-only && bash update.sh`.

Тесты выполнятся до замены контейнера, `.env`, конфигурация и `data` сохранятся. Обновление не создаёт резервную копию автоматически — перед ним можно выполнить `/backup`.

Если уведомлений нет, проверьте `/status` и `sudo docker compose logs --tail=100`. В логах `[SEARCH]` показывает начало запроса, `[SEARCH OK]` — число полученных объявлений и отправленных уведомлений. Первая проверка каждого нового поиска сохраняет старые объявления молча. `/status` показывает ошибки Kufar вместо обычного зелёного статуса. `HTTP 403` означает отказ конкретного адреса API в доступе. Бот пробует два адреса и сохраняет предпочтение рабочего. Локация указывается как причина только если сам Kufar вернул такое объяснение; остальные ответы 403 могут иметь другую причину. Увеличение кеша не исправляет отказ API.

Без сохранённых запросов бот не обращается к поиску Kufar; `/status` показывает «Поиски не настроены» и предлагает добавить запрос. Добавление или удаление поиска через меню прерывает ожидание следующего цикла: новый набор запросов обрабатывается при ближайшем опросе команд (обычно в течение пяти секунд, текущий HTTP-запрос может увеличить задержку). Время последней успешной проверки сохраняется в кеше и переживает перезапуск.

Команда `/check` прерывает ожидание следующего цикла и запускает проверку без очистки истории и повторной инициализации запросов. Если сейчас выполняется HTTP-запрос, бот сначала завершит его. `/status` показывает последние результаты активных поисков в текущем процессе: получено, отфильтровано, уже в кеше, запомнено при первом запуске, отправлено и ошибки отправки. Суммы считаются по поискам, поэтому одно объявление в пересекающихся запросах может учитываться несколько раз. После перезапуска эти счётчики снова появятся при следующих проверках.

Мониторинг получает ограниченную страницу по каждому сохранённому поиску, с сортировкой по новизне (`lst.d`), а не обходит весь Kufar. Старый `sort-type` по цене не применяется к мониторингу: такой порядок мог оставлять новые объявления за пределами первой страницы. По умолчанию запрашивается 30 объявлений; верхний предел страницы — 200. Если за интервал проверки публикуется больше объявлений, чем помещается на странице, часть может быть пропущена: это ограничение проверки одной страницы.

Проверить оба адреса API из работающего контейнера можно без Telegram-запросов, чтения конфигурации и изменений кеша:

```bash
sudo docker compose exec -T bot /app/Kufar-Telegram-Notifier --check-kufar
```

Если контейнер остановлен, используйте `sudo docker compose run --rm --no-deps bot --check-kufar`. Проверка делает по одному запросу «книга» с лимитом 1. Код завершения 0 означает, что хотя бы один адрес вернул корректный массив `ads`; код 2 — оба адреса отказали или вернули некорректный ответ. Пустой корректный массив считается успешным доступом. Если оба адреса возвращают 403, резервный адрес не устранил отказ: нужен анализ доступа с сервера, а не очистка данных. Отказ локации показывается только при соответствующем тексте в ответе Kufar.

Повторно доставленные Telegram-события пропускаются. Перед обработкой каждой команды бот сохраняет номер события и ID сообщения в кеше, чтобы после перезапуска не отвечать повторно. Одно сообщение с новым номером события тоже пропускается; новое нажатие той же кнопки обрабатывается. Если процесс аварийно остановился между сохранением номера и отправкой ответа, повторите команду вручную. В логах `[MENU UPDATE]` показывает принятые ID без текста команды и токена; `/status` показывает версию. На Linux и macOS файл `cached-data.json.lock` запрещает запуск второй копии с тем же кешем; блокировка снимается при завершении процесса, сам пустой файл остаётся. Копии на других серверах или с отдельными кешами нужно остановить отдельно: эта блокировка защищает только общий файл состояния.

Чтобы обновить бота и удалить только запросы владельца (ID из `TELEGRAM_ADMIN_ID`), выполните:

```bash
git pull --ff-only && bash update.sh --clear-my-queries
```

Скрипт собирает образ с обычным кешем, останавливает бота, очищает запросы владельца и запускает обновлённый контейнер. Запросы и кеш остальных пользователей сохраняются. Очистка создаёт резервную копию состояния; история владельца, пользователи и отметки обработанных сообщений тоже сохраняются. Для последующих обычных обновлений используйте `git pull --ff-only && bash update.sh` без параметра очистки.

Отдельная команда для удаления активных запросов всех пользователей:

```bash
git pull --ff-only && sudo docker compose build && sudo docker compose stop bot && sudo docker compose run --rm --no-deps bot --clear-all-queries && sudo docker compose up -d --force-recreate --no-build
```

Очистка не запускает поиск и не обращается к Telegram. Она сохраняет пользователей, историю объявлений, цены и отметки обработанных сообщений; пустые списки перекрывают запросы из конфигурации и переменных окружения при следующих запусках. Исходная конфигурация остаётся на месте. Перед записью создаётся приватная резервная копия `data/cached-data.json.before-clear-*.json`. Если очистка завершилась ошибкой, цепочка не запускает бота; проверьте сообщение и свободное место. Для восстановления при остановленном боте скопируйте выбранную резервную копию поверх `data/cached-data.json`.

```bash
sudo docker compose stop       # остановить, данные сохранить
sudo docker compose up -d      # запустить снова
sudo docker compose logs --tail=100 -f
```

Docker запускает контейнер после перезагрузки сервера, если сервис Docker включён и контейнер не был явно остановлен. Память процесса ограничена 512 МиБ; дампы памяти отключены. Ограничения Compose не применяются к запуску бинарника вручную и не ограничивают ресурсы самой сборки.

Настройки ротации и ресурсов основаны на документации [Docker Compose](https://docs.docker.com/reference/compose-file/services/) и [json-file logging](https://docs.docker.com/engine/logging/drivers/json-file/).
